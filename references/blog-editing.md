## 적용할 때

이 문서는 글 전체를 다듬거나 구성을 맡긴 작업에서 필요할 때 참고한다. 특정 블로그의 문체를 모든 사람에게 적용하는 규격이 아니다. 원문의 정보·경험·높임말과 사용자가 지정한 범위가 우선한다. 게시본에도 오래되거나 불필요한 표현이 남아 있을 수 있다. 반복되는 인삿말이나 빈 부정문까지 모범으로 복제하지 않으며, 사용자의 최신 수정 지시가 게시본의 관행보다 우선한다.

### 1. 계기가 보이는 도입

원문에 있는 변화나 문제로 시작한다. 기술 비교는 비교 대상과 이유, 생활 정보는 독자가 찾는 경로가 먼저 드러나면 좋다. 회고나 서사에서는 장면으로 시작하는 흐름을 존중한다.

창작 예시:

- 전: 빠르게 변화하는 시대에 새로운 서비스가 쏟아집니다. 쓰던 도구의 무료 한도가 줄어 다른 도구를 찾아봤습니다.
- 후: 쓰던 도구의 무료 한도가 줄어 다른 도구를 찾아봤습니다.

앞부분을 줄이기 위해 없던 사건, 날짜, 경험을 만들어 넣지 않는다.

### 2. 수치 뒤에는 의미, 조건은 수치 곁에

표에 있는 값을 본문에서 모두 반복하기보다 그 차이가 어떤 선택에 관련되는지 설명한다. 이때 근거에 없는 추천을 만들어내지 않는다. 작업당 비용과 토큰당 가격, 개발사 평가와 사용자 경험, 서로 다른 설정을 섞지 않는다.

창작 예시:

- 전: 작업당 비용은 A가 2달러, B가 5달러였다. A는 기본 설정, B는 높은 추론 설정이었다.
- 후: 작업당 비용은 기본 설정의 A가 2달러, 높은 추론 설정의 B가 5달러였다.

서로 다른 출처의 가격이나 조건이 충돌하면 임의로 하나를 정답으로 만들지 않는다. 원문에 있는 시점·출처 차이와 확인 방법을 유지한다.

두 결과를 같은 조건에서 얻었다고 덧붙이면 실패다. 공개된 수치라는 이유만으로 신뢰성을 보장한다고 쓰지도 않는다.

### 3. 용어는 쓰이는 곳에서 짧게

원문에 설명이 있으면 첫 등장 주변에 자연스럽게 잇는다. 쉬운 표현으로 바꾸더라도 기술적 구분은 유지한다. 모르는 개념의 설명을 추측해서 추가하지 않는다. 설명을 넣어야 하는데 근거가 없으면 필요성을 짧게 제안한다.

### 4. 정보 글과 경험 글의 밀도를 다르게

정보 글은 링크·조건·행동을 찾기 쉽게 만들고, 후기나 개발기는 선택의 이유·실패·망설임을 남긴다. “두 번 헤매고 나니 익숙해졌다”는 단순한 기능 설명과 다른 정보다. 1인칭이라는 이유만으로 삭제하지 않는다.

### 5. 실제 다음 단계로 마무리

원문에 이미 있는 선택이나 남은 문제로 마무리한다. “앞으로 더 써보겠다” 같은 약속이나 “무한한 가능성” 같은 상투적인 기대를 자동으로 붙이지 않는다. 독자에게 필요한 링크가 있다면 유지한다.

## 선택 가능한 기술 블로그 설정

사용자가 비슷한 기술 블로그 형식을 원한다고 했을 때만 한다체, 짧은 소제목, 비교표, 제한적인 강조를 선택할 수 있다. 표는 비교 축이 실제로 있을 때만 쓴다. 이메일·후기·개인 회고의 말투를 이 설정으로 덮어쓰지 않는다.
